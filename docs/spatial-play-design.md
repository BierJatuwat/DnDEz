## 0. ทำไมต้องมีเอกสารนี้

Sprint F ทำ UI ครบทุก endpoint ที่ backend มี แล้วผลลัพธ์คือหน้าจอที่ **"มีแต่ช่องให้กรอก"** —
ผู้เล่นต้องพิมพ์ `1d20+5` เอง เลือกเป้าจาก dropdown ที่ไม่สนใจว่าอยู่ไกลแค่ไหน และตั้งชื่อตัวละคร
แล้วได้ HP 10/10 ตายตัว

อาการทั้ง 4 อย่างนี้ **ไม่ใช่ปัญหา UI แยกกัน 4 อัน** แต่เป็นอาการเดียวกันจากสาเหตุเดียวกัน:

> **ทุกช่องว่างที่ระบบไม่รู้คำตอบ ถูกอุดด้วยการให้มนุษย์พิมพ์เอาเอง**

ซึ่งขัดกับ concept ตั้งต้นของโปรเจกต์โดยตรง — *"คนไม่เข้าใจก็เล่นและ enjoy กับ D&D ได้"*

### โซ่ dependency ของ concept นี้

```
คลัง SRD (กลไก) → preset → ตัวละครมีความสามารถจริง
                                    ↓
                    แผนที่ + geometry layer
                                    ↓
                         affordance panel
                                    ↓
              ผู้เล่นเห็นว่า "ทำอะไรได้บ้าง ราคาเท่าไร"
```

**ต้องมีครบทุกข้อต่อ** ขาดข้อใดข้อหนึ่ง ช่องว่างตรงนั้นจะกลับไปเป็นช่องกรอกทันที
ตอนนี้ (2026-09-04) **ไม่มีข้อต่อไหนอยู่เลยสักข้อ**

## 1. หลักการที่ตัดสินแล้ว

### 1.1 แผนที่คือแหล่งความจริงเชิงพื้นที่ ไม่ใช่ภาพประกอบ

ลำดับเหตุผล:

```
ตำแหน่งบนแผนที่ → ระยะระหว่างตัวละคร → เทียบกับระยะเอื้อม/ระยะของท่านั้น
    → รายการสิ่งที่ทำได้จริง พร้อมราคาของแต่ละทาง
```

> **หน้าจอกลาง (แผนที่) คือ input ของ rules engine · พาเนลรอบข้างคือ output**

พาเนลข้างจึงไม่ใช่ฟอร์มให้เลือกว่าจะโจมตีใคร แต่เป็น**ผลลัพธ์ที่คำนวณมาแล้ว** — ศัตรูที่อยู่ไกลเกิน
ไม่ปรากฏในลิสต์ตั้งแต่แรก ไม่ใช่ให้เลือกแล้วค่อยเด้ง error

### 1.2 server คำนวณ ไม่ใช่ client

**ผู้เล่นต้องไม่ได้รับตำแหน่งของสิ่งที่ยังไม่เปิดเผย** — ไม่ใช่ส่งไปให้หมดแล้วซ่อนด้วย CSS

⚠️ **รายการ "สิ่งที่ทำได้" เป็นช่องรั่วของข้อมูลในตัวมันเอง** — ถ้าพาเนลบอกว่า *"โจมตีก็อบลินได้"*
ผู้เล่นก็รู้แล้วว่ามีก็อบลินอยู่ **แค่ไม่วาด token ไม่พอ** ตัวรายการต้องคำนวณจาก
"สิ่งที่คนนั้นมองเห็น" เท่านั้น ไม่ใช่คำนวณจากความจริงทั้งหมดแล้วค่อยกรองตอนวาด

เป็นบทเรียนเดียวกับ Sprint F งานที่ 7 (combat endpoint ส่ง AC ของ NPC ที่ซ่อนอยู่ออกไปทั้งที่ UI
ไม่แสดง) แต่ของที่รั่วได้คราวนี้คือ **"มีอยู่ไหม"** ซึ่งแรงกว่า **"เลขเท่าไร"**

มีการซ่อนสองชั้นที่ต้องไม่ปนกัน:

| ชั้น | ความหมาย | มีอยู่แล้วไหม |
|---|---|---|
| fog of war | ไม่รู้ว่า**มีตัวตน** | ยังไม่มี |
| ซ่อน stat NPC | เห็น token แต่**ไม่เห็นตัวเลข** | ✅ Sprint F งานที่ 7 |

### 1.3 affordance เป็น rules engine ไม่ใช่ AI **[แก้ของเดิม — player-side-design §7]**

`player-side-design.md §7` มี *"Panel แนะนำ action (ตาฉันแล้ว ทำอะไรได้บ้าง)"* อยู่แล้ว แต่ออกแบบไว้
เป็น **AI เสนอตัวเลือก** จึงมีข้อจำกัดพ่วงมาเต็ม (ต้องมี API key ของตัวเอง, opt-in ต่อคน,
ผลขึ้นจอ DM ก่อน)

**สิ่งที่เอกสารนี้พูดถึงเป็นคนละอันกัน** — เดินได้ถึงไหน เอื้อมถึงใคร ร่ายตอนประชิดแล้วติด
disadvantage ไหม ล้วนเป็นการคำนวณที่มีคำตอบตายตัว **ไม่ต้องใช้ AI เลย** อยู่หมวดเดียวกับ
`ActionEconomyResolver` ที่มีอยู่แล้ว

| | AI suggestion (§7 เดิม) | affordance (deterministic) |
|---|---|---|
| ค่า token | เปลืองทุกครั้ง | **ศูนย์** |
| ความถูกต้อง | น่าจะถูก | **ถูก 100% เขียนเทสต์ได้** |
| ใครใช้ได้ | เฉพาะคนมี key / opt-in | **ทุกคน ตลอดเวลา** |
| ขึ้นจอไหน | ต้องผ่าน DM ก่อน | **ขึ้นจอผู้เล่นตรงได้** |
| ชนกฎ "AI ห้ามสั่งแทนผู้เล่น" ไหม | ต้องระวัง | **ไม่เกี่ยว ไม่มี AI** |

**ผลที่ตามมา:** ข้อ ⏳ ที่ §7 ค้างไว้ (*"โหมด online ที่ DM ไม่ได้พูดสด การขึ้นจอ DM อย่างเดียว
อาจช้าไป"*) **หมดไปเอง** สำหรับกรณีทั่วไป เพราะตัวเลือกที่ถูกกฎขึ้นจอผู้เล่นตรงเสมอ
ส่วน AI suggestion ยังคงกฎเดิมของมันไว้ได้ไม่ต้องแก้ — มันไปทำงานเรื่องความคิดสร้างสรรค์/
บทบาทสมมติ ซึ่งเป็นคนละงาน

> concept *"ไม่เข้าใจก็เล่นได้"* **ถูกเสิร์ฟด้วย rules engine ได้ดีกว่า AI** —
> มือใหม่ได้คำแนะนำที่ถูกเสมอ ทันที ฟรี ไม่ต้องขอใคร

### 1.4 โมเดล 3 ระดับของตัวเลือก

| ระดับ | ทำอะไร | ตัวอย่าง |
|---|---|---|
| 1. ทำไม่ได้ | ไม่เสนอ (หรือบอกว่าเอื้อมไม่ถึง) | ศัตรูอยู่นอกระยะทุกท่า |
| 2. **ทำได้ แต่มีราคา** | เสนอ **พร้อมป้ายเหตุผลภาษาคน** | *"ร่ายเวทระยะไกลตอนศัตรูประชิด → ติด disadvantage"* |
| 3. ทำได้ปกติ | เสนอเฉย ๆ | — |

**ข้อ 2 คือหัวใจของ concept** — ระบบไม่ห้าม ไม่ตัดสินใจแทน แต่**บอกราคาของทางเลือกให้ครบก่อนกด**
ผู้เล่นเรียนกฎจากการเห็นป้ายซ้ำ ๆ โดยไม่ต้องเปิดหนังสือ

แตะที่ป้ายแล้วอธิบายต่อได้ = pattern เดียวกับ §13 condition tooltip (ดึงจาก `RulesCorpus` ไม่เรียก AI)

**โมเดลนี้ใช้กับ "เส้นทาง" ได้ด้วย ไม่ใช่แค่ "เป้าหมาย"** — ดู §3.4

## 2. คลังกลไก (action catalog)

### 2.1 ⚠️ "import SRD" มีสองความหมายที่ปนกันไม่ได้

`rules_corpus_entries` ที่มีอยู่มีคอลัมน์: `category · key · title · content (text) · license · source`

นี่คือ **คลังข้อความ** เหมาะกับ tooltip แต่ **คำนวณไม่ได้** — จะถามว่า *"ก็อบลินอยู่ในระยะ Fire Bolt
ไหม"* ต้องการ `range: 120` เป็นตัวเลข ไม่ใช่ย่อหน้าอธิบาย

| | คลังข้อความ | คลังกลไก |
|---|---|---|
| ตอบคำถาม | "กฎข้อนี้ว่าอะไร" | "ทำได้ไหม / ถึงไหม / เสียอะไร" |
| รูปแบบ | ข้อความอิสระ | ตัวเลข + ประเภทที่ engine อ่านได้ |
| ใช้โดย | tooltip, อธิบายให้คน | rules engine, affordance panel |
| ตาราง | `rules_corpus_entries` ✅ มีแล้ว | **ยังไม่มี ต้องสร้าง** |

ถ้ายัดสองอย่างนี้ลงตารางเดียวกัน จะจบที่ engine ต้อง parse ข้อความอังกฤษหาว่าระยะกี่ฟุต

### 2.2 catalog เก็บ "มันคืออะไร" — engine ถือ "แล้วยังไง"

*"ร่ายเวทระยะไกลตอนศัตรูประชิด → disadvantage"* **ไม่ใช่คุณสมบัติของ Fire Bolt** แต่เป็นกฎทั่วไป
ที่ใช้กับ *ทุกอย่างที่เป็นการโจมตีระยะไกล*

- **catalog บอกแค่**: Fire Bolt เป็นการโจมตีเวทระยะไกล ระยะ 120 ฟุต
- **engine รู้เอง**: "การโจมตีระยะไกล + มีศัตรูประชิด = disadvantage"

→ กฎเดียวครอบทุกเวท ทุกอาวุธ ทุกมอนสเตอร์ ตลอดไป

ถ้าทำกลับกัน (เขียนเงื่อนไขไว้ในทุกรายการ) ต้องเขียนซ้ำหลายร้อยครั้ง และผิดพร้อมกันทั้งชุดถ้าเข้าใจกฎผิด

**กลไกรองรับมีอยู่แล้ว**: `AdvantageResolver.Resolve(hasAdvantage, hasDisadvantage)` รวมหลายแหล่ง
ตามกฎ 2024 (มีทั้งคู่ = หักล้าง) — ที่ขาดคือ**คนตัดสินว่า `hasDisadvantage = true`**
ซึ่งต้องรู้ระยะกับชนิดของท่าถึงจะคิดได้

### 2.3 สิ่งที่ catalog ต้องบอก — น้อยกว่าที่คิด

| ต้องรู้ | ตัวอย่าง | ใช้ทำอะไร |
|---|---|---|
| ระยะ | ประชิด 5 ฟุต · ไกล 80/320 · เวท 60 ฟุต | กรองว่าเป้าไหนอยู่ในระยะ |
| ชนิดเป้า | ศัตรู · เพื่อน · จุดบนแผนที่ | รู้ว่าจะเสนอใครให้เลือก |
| ราคา | action / bonus / reaction · ช่องเวทระดับ N | ตัดตัวเลือกที่ทรัพยากรหมด |
| รูปทอย | โจมตี vs AC · หรือให้เป้า save | ประกอบ roll ส่งเข้า resolver เดิม |
| ป้ายประเภท | "โจมตีระยะไกล", "เวท", "ต้องเห็นเป้า" | ให้ engine หยิบกฎทั่วไปมาใช้ |

**รายละเอียดที่เหลือทั้งหมด** (คำบรรยาย, upcast, องค์ประกอบการร่าย, ผลพิเศษ) **ไม่ต้องเข้ามาใน
layer นี้** — อยู่ใน jsonb ต่อได้ตามเดิม

### 2.4 รวมอาวุธ + เวท + action ของมอนสเตอร์ เป็นของอย่างเดียว

มือใหม่ไม่ได้คิดว่า *"นี่อาวุธหรือเวท"* — เขาคิดว่า ***"ฉันทำอะไรกับก็อบลินตัวนั้นได้"***

ในสายตา engine ทั้งสองอย่างหน้าตาเหมือนกันเป๊ะตามตาราง §2.3 ต่างแค่รายละเอียดชั้นล่าง
(ช่องเวท, concentration) ถ้าแยกเป็นสองระบบ การคำนวณ affordance จะต้องเขียนสองชุดตลอดไป

**และต้องครอบ NPC/monster ด้วย** — DM คุม NPC และ OA ของมอนสเตอร์ก็ต้องรู้ระยะเอื้อมเหมือนกัน
ตอนนี้ `monster_stat_blocks.actions` เป็น jsonb แยกไปอีกทาง ถ้าปล่อยไว้จะกลายเป็น**สามระบบ
ที่คำนวณเหมือนกันแต่คนละโค้ด**

**การเคลื่อนที่ก็เป็น catalog entry เหมือนกัน** — เดิน/กระโดด/ปีน/บิน/Dash/Misty Step
ล้วนมีราคาและมีกฎ ถ้าอยู่คลังเดียวกันก็ได้ประโยชน์เดียวกัน: **หน้าจอผู้เล่นมีลิสต์เดียว**

### 2.5 ⚠️ ค่าความสามารถ 6 ค่าหายไปจาก `Character`

Sprint B Part 2 ย้าย HP/AC ออกจาก `Sheet` jsonb เป็น typed column ด้วยเหตุผลที่เขียนไว้ใน comment:

> *"ทุกตัวละครมีแน่นอน ไม่ผันแปรตามคลาส"* → typed column · ที่ผันแปรจริงอยู่ `Sheet` ต่อไป

ใช้เลนส์เดียวกัน: **STR/DEX/CON/INT/WIS/CHA เป็นของที่ทุกตัวละครมีแน่นอนยิ่งกว่า HP ด้วยซ้ำ**
แต่ตอนนี้ **ไม่มีใน `Character` เลย** ค่าโจมตี `+5` จึงไม่มีที่มา ต้องให้คนกรอกเอง — ขัด concept ตรง ๆ

เช่นเดียวกับ `speed` (ตอนนี้ hardcode 30 ฟุตใน `EncounterEndpoints.DefaultMovementFeet`
พร้อม comment ยอมรับว่าชั่วคราว) และ reach/range ที่ไม่มีที่ไหนเลย

## 3. Geometry layer

`PROJECT-CONTEXT §4` เขียนไว้ตั้งแต่ตอนวางแผน rules engine ว่า:

> *"เลื่อน **spellcasting เต็มรูป** กับ **fog of war** ไว้ (fog ต้องรอ **grid/geometry layer** ก่อน)"*

ชิ้นที่ขาดจึงมีชื่อในคำศัพท์ของโปรเจกต์อยู่แล้ว และทุกอย่างในเอกสารนี้ยืนอยู่บนมัน

### 3.1 "เดินได้ถึงไหน" คือ pathfinding ไม่ใช่วงกลม

ค่าใช้จ่ายการเคลื่อนที่ = ฟังก์ชันของ **(เส้นทาง, วิธีเคลื่อนที่, พื้นแต่ละช่องบนเส้นทาง, effect ที่ติดตัว)**

ไม่ใช่ `ระยะทาง × ตัวคูณพื้น`

> ถ้ามีพื้นเดินยากขวางอยู่ ช่องที่ไกลเท่ากันจะไปถึงได้ไม่เท่ากัน และบางทีอ้อมไกลกว่ากลับถูกกว่าลุยตรง
> — ระบบต้องหาทางที่ถูกที่สุดให้เอง

⚠️ **`player-side-design.md §4` เขียนว่า "movement แสดง...+ วงรัศมีบนแผนที่"** — วงรัศมี
**ใช้ไม่ได้** เมื่อมีพื้นเดินยาก ต้องเป็นการกระจายตามต้นทุน **[แก้ของเดิม]**

### 3.2 วิธีเคลื่อนที่กำหนดว่าพื้นมีผลไหม

> **"ผ่านช่องนั้น" ไม่ใช่คำถามเดียว — ต้องรู้ว่า *ผ่านยังไง* ด้วย**

- เดินผ่านพื้นเดินยาก → คิดผลของพื้น
- กระโดดข้าม / ปีนข้าม / บินข้าม → **ไม่คิด**

catalog entry ของแต่ละวิธีเคลื่อนที่ประกาศแค่ว่า **"แตะพื้นหรือไม่"** แล้ว engine ถือกฎกลางว่า
*"ถ้าแตะพื้น ให้คิดผลของพื้น ถ้าไม่แตะ ไม่ต้องคิด"* — กฎเดียวครอบทั้งกระโดด ปีน บิน
และของที่ยังไม่ได้เพิ่มในอนาคต

> ⚠️ รายละเอียดกฎจริง (กระโดดข้ามพื้นเดินยากคิดยังไงตอนลงพื้น ฯลฯ) **ยังไม่ได้ตรวจกับ SRD 5.2**
> ต้องเช็คตอนลงรายละเอียด — ที่ตกลงกันวันนี้คือ**โครงสร้าง** ไม่ใช่ตัวเลข

### 3.3 พื้นมีสองแหล่ง — ต้องเก็บแยกกัน

| | **พื้นจากแผนที่** | **พื้นจาก effect** |
|---|---|---|
| ตัวอย่าง | หนองน้ำ, ซากปรักหักพัง | Web, Grease, Spike Growth |
| เกิดเมื่อไหร่ | DM วาด/นำเข้าล่วงหน้า | เกิดกลางเกม หายเมื่อหมดเวลา |
| อยู่ที่ไหน | `scenes.grid` (jsonb มีแล้ว) | ผูกกับ encounter ไม่ใช่แผนที่ |

ฟังก์ชันคิดค่าเคลื่อนที่อ่าน**ผลรวมของทั้งสองชั้น** — ถ้าเก็บรวมกัน พอเวทหมดเวลาจะไม่รู้ว่าต้อง
ลบอะไรออก และแผนที่จะสกปรกถาวร

**"สกิลที่จำกัดการเคลื่อนที่"** (ถูกจับล็อก, โดนชะลอ, speed = 0) เป็น **effect ที่ติดตัวละคร**
ไม่ใช่ติดพื้น — คนละแกน แต่เข้าสมการเดียวกันตอนคำนวณ

### 3.4 OA และการเลือกเส้นทาง

การเคลื่อนที่ทริกเกอร์ reaction ได้ → **เส้นทางมีผลทั้งกับราคาและกับผลที่ตามมา** ทำให้เกิดความต่าง
ระหว่าง "ทางที่ถูกที่สุด" กับ "ทางที่ปลอดภัยที่สุด"

ตามโมเดล 3 ระดับ (§1.4) ระบบต้อง**บอกก่อนกด**:

> *"ทางนี้ใช้ 25 จาก 30 ฟุต และจะโดนโจมตีสวนตอนออกจากระยะก็อบลิน"*

**นี่คือจุดที่ทำให้ OA ไม่ใช่กับดักที่มือใหม่เหยียบโดยไม่รู้ตัว แต่เป็นข้อมูลที่เห็นก่อนตัดสินใจ**

**ของที่มีอยู่แล้วและจะได้ใช้จริงตรงนี้**: `campaigns.reaction_timeout_seconds`
(ดีฟอลต์ 30 วิ, constraint 5–300) มีมาตั้งแต่ InitialSchema แต่ **ไม่มีโค้ดที่ไหนใช้เลย** —
มีแค่ส่งค่าออก API · `player-side-design §4` ออกแบบ reaction prompt + timeout ไว้แล้วเช่นกัน

## 4. ที่มาของข้อมูล — สอง pipeline ที่ห้ามปนกัน

**ยืนยันกับเจ้าของโปรเจกต์ 2026-09-04**: ที่ DM สแกนเข้ามาเองคือ **เนื้อเรื่องในการเล่น**
(หนังสือผจญภัย) ไม่ใช่กฎ

| | **กฎ (SRD)** | **เนื้อเรื่อง (DM สแกน)** |
|---|---|---|
| ขอบเขต | ทั้งระบบ ใช้ร่วมกัน | ต่อแคมเปญ |
| ที่มา | เรา preload เอง | DM อัปโหลดหนังสือของตัวเอง |
| เปลี่ยนบ่อยไหม | แทบไม่ (ตามเวอร์ชัน SRD) | ทุกแคมเปญไม่เหมือนกัน |
| ความน่าเชื่อถือ | เราคุมคุณภาพเอง | extraction ผิดได้ → **ต้องผ่าน DM review** |
| ตาราง | `rules_corpus_entries` (ไม่มี `campaign_id`) | `source_documents` → `story_beats` / `npc_profiles` / `monster_stat_blocks` / `map_assets` |

หลักฐานที่ชี้ชัด: **`rules_corpus_entries` ไม่มีคอลัมน์ `campaign_id`** = ของระดับระบบ ส่วน
`source_documents` มีทั้ง `campaign_id` และ `owner_user_id`

**สรุปที่ตัดสินแล้ว: คลังกลไกของอาวุธ/เวท มาจาก SRD ที่เรา preload อย่างเดียว ไม่รับจากสแกน** —
ตัดความเสี่ยงที่ extraction อ่านระยะเวทผิดแล้วไปหลอกผู้เล่นออกทั้งก้อน

เรื่องหลายเวอร์ชันเผื่อทางไว้แล้ว: `campaigns.rules_system` เป็นคอลัมน์ที่มีอยู่ (fixture ใช้ `srd2024`)
ช่วงแรกยึด **SRD 5.2** (CC-BY-4.0 ฝังลงระบบได้เลย ตาม PROJECT-CONTEXT §2)

### 4.1 ⚠️ แต่กลไกของมอนสเตอร์ยังมาจากสแกนอยู่ดี

`monster_stat_blocks` มี `armor_class`, `hit_points`, `actions` (jsonb) พร้อม `source_document_id` —
เพราะมอนสเตอร์เฉพาะของผจญภัยเล่มนั้นไม่ได้อยู่ใน SRD **เลี่ยงไม่ได้และถูกต้องแล้ว**

แต่พอเอาข้อมูลนี้ไปคำนวณ affordance **น้ำหนักของด่าน DM review เปลี่ยนไป**:

| | เดิม | หลังมี affordance panel |
|---|---|---|
| extraction อ่านผิด | ตัวเลขบนการ์ดผิด | ระบบบอกผู้เล่นว่า *"เดินตรงนี้ปลอดภัย"* ทั้งที่โดน OA |
| ใครจับได้ | DM เห็นเองว่าแปลก | **ไม่มีใครจับได้** |

เอกสารเดิมให้เหตุผลของด่าน review ว่า *"ถ้า HP ผิดเกมพัง"* — พอมี affordance panel
**ความผิดพลาดจะเงียบกว่าเดิม เพราะทั้งระบบสร้างมาเพื่อให้ผู้เล่นไม่ต้องรู้กฎ**

> **ข้อกำหนดที่ตามมา**: ตอนออกแบบหน้า DM review ให้ **ระยะ/reach ของ action เป็นฟิลด์ที่ DM
> ต้องยืนยันเสมอ** ไม่ใช่ผ่านไปเงียบ ๆ

## 5. Character preset — ออกแบบครบแล้ว ยังไม่มีใครสร้าง

`player-side-design.md §18–19` ออกแบบไว้ครบ และ **schema ลงไปแล้วแบบ 1:1**

| คอลัมน์จริงใน `character_presets` | ตรงกับข้อไหน |
|---|---|
| `scope` (global/campaign) | §18 "DM สร้าง preset ของแคมเปญตัวเองได้" |
| `source` (authored/harvested) | §18 คลังกลาง vs §19 harvest จากตัวละครที่เล่นจริง |
| `build` jsonb | §19 "เก็บแค่ race/class/subclass/ability/feat/spell/equipment" |
| `level_path` jsonb | §18 "auto-level แบบ deterministic" |
| `build_fingerprint` | §19 "dedupe ด้วย fingerprint แล้วนับ popularity แทน" |
| `popularity_count` | §19 ของแถม — เอาไปเรียงลำดับในคลัง |
| `srd_only` | §19 กฎข้อ 3 — ของจาก source scan ห้ามเข้าคลังกลาง |

`Character.HarvestConsent` = §19 กฎข้อ 1 (ไม่ติ๊ก = ลบทิ้งจริง)

**ที่มีอยู่ตอนนี้เป็น placeholder ล้วน** — กรอกชื่ออย่างเดียว ได้ HP 10/10, AC 10, level 1 ตายตัว

### 5.1 preset กับ catalog เป็นปัญหาเดียวกัน

`build` เก็บ *"spell / equipment"* ซึ่งคือ**การอ้างอิงเข้าไปในคลังกลไก** (§2)

- ไม่มีคลังกลไก → preset เป็นตัวเลขที่ไม่มีความหมาย ("มีดาบยาว" แต่ระบบไม่รู้ว่าดาบยาวคืออะไร)
- มีคลังกลไก → เลือก preset ปุ๊บ ตัวละครมีอาวุธ/เวทจริงที่ engine คำนวณต่อได้ทันที

> **preset คือทางที่คลังกลไกเดินไปถึงผู้เล่นโดยที่เขาไม่ต้องพิมพ์อะไรเลย**
> — กด "นักรบ level 1" แล้วได้ดาบยาวกับโล่มาเลย ไม่ต้องรู้ว่าดาบยาวทอย 1d8

### 5.2 งานที่หลบไม่ได้: preset ชุดแรก

§19 ยอมรับไว้เองว่าคลัง harvest **เริ่มจากศูนย์** (cold start) ช่วงแรกไม่มีใครเล่นจบ session ให้เก็บ

→ ต้องมี preset ที่เราเขียนเองไว้ก่อน (`source: authored`) ประมาณ **6–12 ตัวครอบคลาสพื้นฐาน
level 1 พร้อม `level_path`**

เป็นงาน **"เขียนข้อมูล" ไม่ใช่เขียนโค้ด** แต่อยู่บนเส้นทางวิกฤต — ถ้าไม่มี ผู้เล่นใหม่คนแรกจะเปิด
คลังมาเจอที่ว่าง ซึ่งแย่กว่าไม่มีคลังเลย

## 6. ผลกระทบต่อ realtime

ตอนนี้ทุก event ยิงเป็น `Clients.Group(campaign:{id})` = ทุกคนได้ payload ก้อนเดียวกัน
(Sprint F งานที่ 7 ต้องแหกกฎนี้ไปแล้วครั้งหนึ่ง — HpUpdated ของ NPC ที่ซ่อน stat ต้องส่งเฉพาะ DM)

**พอมี fog ต่อคน ทุก update ของแผนที่จะมีเนื้อหาต่างกันตามคนดู** ทางเลือก:

| | ส่งแยกรายคน | ส่งสัญญาณ "มีอะไรเปลี่ยน" แล้วให้ client ไป GET เอง |
|---|---|---|
| ความถูกต้อง | ถูก แต่ logic สิทธิ์กระจายทุกจุดที่ broadcast | **จุดตัดสินสิทธิ์รวมที่ endpoint เดียว** |
| latency | เร็วกว่า | ช้ากว่า 1 round-trip |
| โอกาสพลาด | สูงกว่า | ต่ำกว่า |

**เอนเอียงไปทางที่สอง** — เข้ากับที่ Sprint F งานที่ 6b ทำอยู่แล้ว (combat event → invalidate query)
แต่ยังไม่ตัดสิน เพราะการลาก token อาจรู้สึกหน่วง

## 8. ข้อเสนอฝั่ง Player จากการคุยรอบนี้

ทุกข้อเป็น deterministic ไม่ใช้ AI ไม่เปลือง token

### 8.1 ทำได้เลย ต้นทุนต่ำ ใช้ของที่มีอยู่แล้ว

**(ก) อธิบาย "ทำไม" ของผลลัพธ์ ไม่ใช่แค่บอกผล**

`AttackResult` มี `total`, `targetArmorClass`, `hit`, `outcome` ครบแล้ว แค่ยังไม่ได้แสดง:

> ทอยได้ **14** + โบนัส 5 = **19** · เกราะก็อบลิน 20 → **พลาดไป 1 แต้ม**

"พลาดไป 1 แต้ม" คือจุดที่ความสนุกอยู่ และสอนไปในตัวว่าเลขพวกนี้ทำงานยังไง

**(ข) ขยาย §13 จาก condition ไปทุกศัพท์ในเกม**

UI เป็นภาษาไทยแต่ศัพท์เกมยังเป็นอังกฤษหมด (AC, HP, Bonus action, disadvantage, saving throw)
มือใหม่ไม่รู้ว่า "AC" คืออะไรตั้งแต่คำแรก — ใช้ตาราง `rules_corpus_entries` เดิม
**ได้คำศัพท์ทั้งเกมจากกลไกที่ทำครั้งเดียว**

**(ค) ออกแบบสำหรับตอนที่ *ไม่ใช่* ตาตัวเอง**

โต๊ะ 4 คน = ได้เล่นแค่ ~25% ของเวลา อีก 75% คือตอนที่มือใหม่หลุดโฟกัส — เอกสารเดิมยังไม่มี
ส่วนไหนออกแบบช่วงนี้ (mockup รูปที่ 3 คือหน้าจอนี้พอดี: ข้อมูลครบ ไม่มีปุ่มสั่งเลย)

รวมกับข้อ (ก) จะกลายเป็นช่วงเรียนรู้ — **มือใหม่เรียนกฎจากการดูคนอื่นเล่น** ซึ่งเป็นวิธีที่คนเรียน
D&D กันจริงที่โต๊ะ · บวกกับให้เห็นว่าอีกกี่คิวจะถึงตาเรา (มีข้อมูลลำดับอยู่แล้ว)

### 8.2 💡 เก็บไว้เป็นไอเดีย — ยังไม่ตัดสิน

ตัดสินใจร่วมกัน 2026-09-04 ว่าน่าสนใจแต่ยังไม่เอาเข้าแผน

**(ง) แสดง "ความน่าจะเป็น" แทน "คำแนะนำ"**

โอกาสเข้า (จากโบนัสโจมตี vs AC) + ดาเมจเฉลี่ย — เป็นเลขคณิตล้วน ระบบไม่ได้บอกว่าควรเลือกอันไหน
แค่แสดงเลขที่คนคิดในหัวไม่ทัน **ผู้เล่นยังตัดสินใจเอง** จึงไม่ชนกฎที่ล็อกไว้

⚠️ **ปมที่ต้องแก้ก่อน**: การคำนวณต้องรู้ AC ของเป้า แต่ Sprint F งานที่ 7 ให้ DM ซ่อน AC ของ NPC ได้
— โชว์ % ตรง ๆ = บอก AC กลับด้าน (ถอดสมการย้อนได้) ทางออกที่คิดไว้: เป้าที่ซ่อน stat ไม่โชว์ %
หรือโชว์เป็นระดับหยาบ ("ยาก/ปานกลาง/ง่าย")

**(จ) Undo ที่ DM อนุมัติ**

โต๊ะจริงมีเสมอ (*"อ้าว เอาใหม่ได้"*) ระบบดิจิทัลมักล็อกตายแล้วมือใหม่เกร็ง ไม่กล้ากดอะไร
ซึ่งกิน enjoy โดยตรง — ไม่มีในเอกสารเดิม (§6 DM override เป็นคนละเรื่อง)

เส้นแบ่งที่คิดไว้: **ย้อน "การตัดสินใจ" ได้ · ย้อน "โชค" ไม่ได้**
- ก่อนทอย → ยกเลิกการประกาศ action ได้เสรี
- หลังทอย → ต้อง DM อนุมัติ และ **ต้องขึ้น log ว่าย้อน** ไม่ใช่ลบเงียบ ๆ

## 11. กฎเหล็กของ route: ทุก endpoint ต้องมี `/campaigns/{campaignId}` นำหน้า

**ไม่ใช่เรื่องความสวยงามของ URL — เป็นเงื่อนไขให้ RLS ทำงาน**

RLS middleware อ่าน campaign จาก **route value** โดยตรง (`Program.cs` — middleware ที่ครอบทุก request):

```csharp
context.Request.RouteValues.TryGetValue("campaignId", out var rawCampaignId)
    && Guid.TryParse(...)  →  SET LOCAL app.campaign_id
```

และ policy ทุกตัวใน migration `RowLevelSecurity` เขียนว่า:

```sql
USING (campaign_id = app_current_campaign() AND app_is_member())
-- app_current_campaign() = NULLIF(current_setting('app.campaign_id', true), '')::uuid
```

`current_setting(..., true)` คืนค่าว่างเมื่อไม่ได้ตั้ง → NULL → `campaign_id = NULL` →
**NULL → กรองทุกแถวทิ้ง**

> ⚠️ **route ที่ไม่มี `{campaignId}` จะไม่ error — มันจะ "ไม่เห็นข้อมูลอะไรเลย" เงียบ ๆ**
> (fail closed ซึ่งปลอดภัย แต่ดีบักยากมาก เพราะดูเหมือนข้อมูลหาย ไม่ใช่สิทธิ์ถูกปฏิเสธ)

`scenes` หนักกว่านั้นเพราะ policy อ้อมผ่าน session:

```sql
EXISTS (SELECT 1 FROM sessions s
        WHERE s.id = scenes.session_id AND s.campaign_id = app_current_campaign())
```

**ตรวจแล้ว 2026-09-05**: endpoint ที่มีอยู่ทั้งหมด (30 route) ไม่มีข้อยกเว้นเลยแม้แต่ตัวเดียว —
แม้แต่ `/campaigns/{cid}/encounters/{eid}/next-turn` ที่ `eid` unique ทั้งระบบอยู่แล้ว
ก็ยังคง prefix ไว้

## 12. active beat — เก็บที่ไหน

**ตัดสิน: เก็บที่ `story_beats.progress` (ระดับแคมเปญ) ไม่เพิ่ม `sessions.active_beat_id`**

`BeatProgress` ที่มีอยู่แล้วคือ `{ Upcoming, Active, Passed }` — **ตรงกับสามสถานะในรูปที่ 1 พอดี**:

| ในรูป | enum |
|---|---|
| `✓ Arrival at port` | `Passed` |
| `▶ Drowned temple` | `Active` |
| `Spire ascent` | `Upcoming` |

คนออกแบบตอนแรกตั้งใจให้ "beat ไหน active" อยู่ที่ตัว beat อยู่แล้ว

| | `story_beats.progress` (เลือกอันนี้) | `sessions.active_beat_id` |
|---|---|---|
| migration | ไม่ต้อง | ต้อง |
| ได้ ✓/▶ ในรูปที่ 1 | ฟรี | ต้องคำนวณเพิ่ม |
| สอง session ของแคมเปญเดียวกัน active คนละ beat | ไม่ได้ | ได้ |

ข้อเสียข้อเดียวไม่ใช่ scenario ที่โปรเจกต์รองรับ — เนื้อเรื่องของแคมเปญเดินเป็นเส้นเดียว
session คือคืนที่เล่น ไม่ใช่เส้นเรื่องคู่ขนาน

**บังคับ invariant ด้วย partial unique index** — โปรเจกต์ใช้ pattern นี้อยู่แล้วกับ `scenes`:

```sql
-- ที่มีอยู่แล้ว: ix_scenes_one_active_per_session UNIQUE (session_id) WHERE is_active = true
-- ที่ต้องเพิ่ม:
CREATE UNIQUE INDEX ix_story_beats_one_active_per_campaign
    ON story_beats (campaign_id) WHERE progress = 'Active';
```

### 12.1 ทำไม active-beat ต้องเป็น endpoint เดี่ยว ไม่ใช่ PATCH ธรรมดา

เปลี่ยน beat ไม่ใช่การแก้ฟิลด์ — มันเป็น **เหตุการณ์ที่ขับทั้งระบบ**:

- Scene prep เปลี่ยนตาม (§13.2)
- จอกลางเปลี่ยนหัวข้อฉาก
- context ที่ส่งเข้า orchestrator เปลี่ยน
- beat เดิม → `Passed` · beat ใหม่ → `Active` (สองแถวในธุรกรรมเดียว)

จึงต้อง broadcast ออกทุก channel และเป็น transaction เดียว — `PATCH` ทั่วไปไม่สื่อความหมายนี้
และเปิดช่องให้ client เผลอตั้ง `Active` สองตัวพร้อมกัน

**path เป็น session-scoped** แม้ state จะอยู่ระดับแคมเปญ เพราะ *การ broadcast* ผูกกับ session
ที่กำลังเล่นอยู่

**คนละหน้าจอ แต่เป็น state เดียวกันที่ถูกกรองคนละแบบ** — แยกให้ชัดว่าอะไรอยู่ชั้นไหน:

## 14. การเคลื่อน token — ephemeral กับ committed

การลาก token ยิงถี่มาก (ลากทีนึงหลายสิบเฟรม) เขียน DB ทุกครั้งไม่ไหว

### 14.1 ⚠️ เขียน state ผ่าน SignalR hub ไม่ได้

ทางแก้ที่ดูตรงไปตรงมาที่สุดคือให้ hub รับตำแหน่งแทน HTTP — **แต่ทำไม่ได้ด้วยเหตุผลเดียวกับ §11**:

> RLS middleware อ่าน `campaignId` จาก **route value** — SignalR invocation **ไม่มี route** →
> `app.campaign_id` เป็น NULL → มองไม่เห็นแถวไหนเลย

hub ปัจจุบันจึงมีแค่ `JoinCampaign` / `LeaveCampaign` (จัดการ group) ไม่เคยเขียน state เลย
ซึ่งไม่ใช่ความบังเอิญ

### 14.2 แบ่งเป็นสองอย่างที่คนละธรรมชาติ

| | **ระหว่างลาก (ephemeral)** | **ตอนวาง (committed)** |
|---|---|---|
| ช่องทาง | broadcast ผ่าน hub | `PATCH .../tokens/{tid}` |
| ใครเชื่อ | ไม่มีใคร — เป็น ghost preview | เป็นความจริง |
| persist | ไม่ | ใช่ |
| ถ้าหาย | ไม่มีผล | ผู้ใช้รู้ทันที |

คนอื่นในโต๊ะเห็น token ขยับตามแบบลื่นไหล แต่ **ไม่มีใครถือว่าเฟรมระหว่างทางเป็นสถานะจริง** —
ยิง HTTP ครั้งเดียวตอนปล่อยเมาส์

### 14.3 Redis เป็นตัวลดจำนวนการเขียน ไม่ใช่ที่เก็บ

**ต่างจาก turn state** ที่ล็อกไว้ว่า *"Redis หาย = รีเซ็ตเทิร์นปัจจุบัน ไม่ใช่ 500"* — ใช้ได้เพราะ
turn state **สร้างใหม่ได้** (`StartTurn` ค่าเดิมเป๊ะ)

**ตำแหน่ง token สร้างใหม่ไม่ได้** — Redis ตายกลางศึกแล้วยอมให้หาย = แผนที่ย้อนกลับไปสถานะเก่า
ต่อหน้าทุกคน กู้เองไม่ได้

ดังนั้น:

- **Postgres (`scenes.tokens`) คือ source of truth เสมอ**
- Redis เป็น write-coalescing layer — ถ้าใช้ไม่ได้ **ให้ถอยไปอ่าน-เขียน Postgres ตรง ๆ**
  (ช้าลงแต่ถูกต้อง) พร้อม log warning ไม่ใช่ยอมให้ข้อมูลหาย
- persist ทันทีที่จุดที่ผู้ใช้รับรู้ว่าเป็นหมุด: **เปลี่ยนเทิร์น · เปลี่ยน fog · จบ encounter ·
  ปิด session** บวก flush ตามเวลาระหว่างนั้น

## 15. autonomy dial คุมอะไร — กฎกลาง

**ตัดสิน: dial คุมเฉพาะสิ่งที่ AI ริเริ่มเอง ไม่คุมสิ่งที่มนุษย์สั่ง**

ปัญหาที่เจอตอนออกแบบ `POST .../scenes/{scid}/generate`: "map-scene" เป็น 1 ใน 4 subsystem ของ dial
และกฎที่ล็อกไว้คือ *"tool call ใน subsystem ที่ตั้งเป็น suggest จะกลายเป็น pending proposal"*

แต่ถ้า **DM กดปุ่ม Generate เอง** แล้วระบบสร้าง proposal ให้ DM มาอนุมัติสิ่งที่ตัวเองเพิ่งกด
= เพิ่มงานให้ DM โดยไม่ได้ความปลอดภัยอะไรเพิ่ม ซึ่งสวนกับเป้าหมาย *"ทำให้ DM ทำงานน้อยลง"*

> **กฎกลาง (ใช้ได้ทุก subsystem ไม่ใช่แค่แผนที่):**
> dial ตอบคำถามว่า *"AI ทำเองได้แค่ไหนโดยที่ไม่มีใครสั่ง"* —
> ไม่ได้ตอบว่า *"มนุษย์กดปุ่มแล้วต้องขออนุญาตใครอีก"*

- `Manual` = orchestrator ไม่แตะ subsystem นั้นเองเลย · ปุ่มที่ DM กดยังทำงานปกติ
- `Suggest` = AI เสนอเข้าคิว proposal
- `Autonomous` = AI ทำเองได้

**แต่ผลลัพธ์ของ generate ต้องผ่าน preview แล้วยืนยันก่อนแทนที่ฉากจริง** — คนละเรื่องกับ proposal gate
(อันนั้นกันไม่ให้ AI เปลี่ยน state ลับหลัง · อันนี้กันภาพที่ scale ผิดหรือใช้ไม่ได้)
ห้าม auto-replace ฉากที่กำลังใช้อยู่เด็ดขาด

## 16. Credential ของจอกลาง

`GameSession.JoinCode` มีอยู่แล้ว แต่ doc comment ระบุว่าเป็น *"รหัสสั้น 6 หลักสำหรับ join
(สำรองจาก QR)"* — เป็นของ **ผู้เล่น**

**ห้ามให้จอกลางใช้โค้ดเดียวกัน** — URL จอกลางที่หลุด (ซึ่งหลุดง่ายเพราะฉายอยู่กลางวง)
จะกลายเป็นทางให้คนนอกเข้าโต๊ะในฐานะผู้เล่น

ข้อกำหนดของ credential จอกลาง:

- **read-only บังคับที่ server** ไม่ใช่แค่ UI ไม่มีปุ่ม
- ผูกกับ **session เดียว** ไม่ใช่ทั้งแคมเปญ
- **เพิกถอน / สร้างใหม่ได้** โดย DM
- ไม่ผูกกับตัวละครใด และไม่สร้างแถวใน `campaign_members`

## 17. โซนแผนที่ — ปุ่มทั้ง 4

บันทึกจากที่คุยกันไว้ (ยังไม่ได้ลงรายละเอียดเต็ม):

| ปุ่ม | ความหมาย |
|---|---|
| **Upload set** | ชุดแผนที่ทั้งแคมเปญ + grid alignment (ต่อกับ `map_assets.grid_alignment`) |
| **Generate with AI** | fallback เมื่อไม่มีแผนที่ — **ล็อก pixel-per-square ไว้** ไม่งั้น grid เพี้ยน |
| **Fog control** | deterministic ล้วน **ไม่ผ่าน AI** |
| **Tokens** | ผูกกับ entity จริง (`characters` / `monster_stat_blocks`) **ไม่ใช่แค่รูปวงกลม** |

ข้อสุดท้ายสำคัญกับภาคแรก — token ที่ผูกกับ entity จริงคือสิ่งที่ทำให้ affordance engine
คำนวณได้ว่า "ตัวนี้เอื้อมถึงตัวนั้นไหม" ถ้า token เป็นแค่รูป จะคำนวณอะไรไม่ได้เลย
